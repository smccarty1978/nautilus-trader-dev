# Subagent Roster — Rationale

Companion to `AGENTS.md` §11. This file explains *why* the roster is what it is, including
the roles that deliberately do not exist. The definitions themselves live in
`.claude/agents/`.

`.claude/agents/*.md` is the **canonical** source. `.agents/agents_staging/*.md` and
`.codex/agents/*.toml` are generated by `python scripts/sync_agents.py`. Do not hand-edit
the generated files.

`.codex/agents/implementation-worker.toml` is **Codex-only** and has no Claude counterpart;
`sync_agents.py` leaves it untouched.

---

## The set

| Agent | Role | Model tier | Cap | Writes |
|---|---|---|---|---|
| `repo-scout` | Repository / architecture mapper. Locate the authoritative implementation, trace call paths and execution closure, flag stale or duplicate paths | Haiku / low | 700w | nothing |
| `lookahead-auditor` | Causality gate. Owns checklist **A, B, C1–C3, F, G, H** | Sonnet / high | 1,500w | own audit artifacts |
| `contract-checker` | Contract / governance gate. Owns **C4, D, E**, deliverables, seals, lifecycle state, model-integrity declarations | Sonnet / medium | 1,000w | own audit artifacts |
| `results-triager` | Bounded pytest runner and output reducer | Haiku / low | 500w | nothing |
| `implementation-worker` | Bounded implementer and repairer (Codex only) | Sonnet-class / medium | — | allowed files in the packet |
| `Explore` | **Model pin, not a role.** Pins the built-in fan-out search agent to Haiku | Haiku / low | 700w | nothing |

Five real roles plus one model pin.

## Why these, and not others

### Why `repo-scout` and `Explore` are both present

`Explore` is a **built-in** agent. Without a project-level definition it inherits the
orchestrator's model, which here is Opus — so a routine "where is X defined?" sweep would
run at orchestrator cost. `.claude/agents/Explore.md` exists solely to pin it to Haiku.

It is not a competing role. For any evidence gathering that feeds a SPEC, a plan, or an
audit, use `repo-scout`: it carries the 700-word contract, is named in `AGENTS.md`, and is
mirrored to Codex and Antigravity.

Deleting `Explore.md` would silently restore Opus-cost discovery. Keep it.

### Why the two auditors are NOT merged

A single "causality / governance auditor" is the obvious simplification, and it is the wrong
one here.

Across ~100 historical audit reports, ~60% of blocking findings were **completeness**
issues (`D1` 22, `C4` 22, `C3` 12, `D4` 9) rather than look-ahead. The causal checklist has
no natural stopping point for completeness, so a combined auditor invents new findings each
pass. `studies/codex_5.6_short_rth_enriched_volume_level_retrain/` ran **18 passes** before
the split.

The split works because the scopes are **disjoint and enforced**: neither agent may report
the other's category, and each writes its own status JSON. That, plus the bounded re-audit
protocol, is what stopped the loop. Merging them re-creates the loop.

They also cannot share a reviewer identity: causal and contract reviews must be authored by
**distinct declared reviewer identities**, verified by `scripts/run_preexec_audits.py`.

### Why there is no separate "research execution agent"

Lifecycle execution is deterministic. `scripts/run_bounded_study.py` enforces time, memory
and stale-progress limits and emits a JSON status card;
`research_workflow/lifecycle.py` sequences the stages; `scripts/reconcile_runs.py`
classifies terminal state by PID liveness.

An LLM in that loop would add cost and a second, weaker source of truth. The repository rule
is explicit: **never use an agent for process monitoring.** The orchestrator reads the status
card.

### Why there is no separate "analysis / decision agent"

Interpreting results, comparing model arms, and deciding whether a finding is real is the
highest-judgement work in this repository — it is where the memorable failures live (a
baseline missing the losers the entry rule pays for; a placebo that was outcome-blind but
not length-blind; an arm delta produced by a dead feature block).

Routing that to a cheaper tier violates the standing rule: **never put a research-blessing
gate on Haiku.** Routing it to a same-tier subagent buys nothing, because the subagent starts
cold and has to re-derive the context the orchestrator already has.

`results-triager` deliberately stops at *deterministic* test triage: command, exit status,
counts, first root failure, artifact paths, one verdict. It never interprets a research
result.

### Why there is no separate "performance agent"

Benchmarking here is already deterministic and already exists:
`scripts/benchmark_historical_same_harness.py` (same-harness historical controls),
`scripts/run_collector_ablation_matrix.py` (ablation on one replay day),
`backtests/nt_runtime/telemetry.py` (opt-in `tracemalloc`, always-on RSS).

The one durable lesson — telemetry must not alter execution performance, and instrumentation
cost must be separated from replay cost — is a rule in `docs/RESEARCH_WORKFLOW.md` §8, not a
role. An agent would only re-run those scripts and paraphrase the numbers.

### Why `implementation-worker` stays Codex-only

Claude's main session does multi-file implementation directly; it holds the architectural
context that makes the change correct. Codex is more often driven from a frozen task packet,
which is exactly what `implementation_worker` requires. Adding a Claude counterpart would
create a delegation hop with no information gain.

## Principles every subagent inherits

From `AGENTS.md` §11:

1. Authoritative implementation first.
2. No duplicate infrastructure.
3. Feature V2 canonical semantics — timeframe is a parameter, never an identity.
4. Causal and TRAIN/OOS correctness above all.
5. Deterministic defects are fixable — repair rather than reporting `BLOCKED`.
6. Targeted tests.
7. Bounded before expensive.
8. No silent dataset substitution.
9. No unsafe recursive cleanup.
10. Exact artifact and provenance reporting.

Every definition states its **input**, **output**, **non-responsibilities**, and
**escalation criteria**. No subagent may spawn another.

---

## Changing this roster

Adding, removing, or re-tiering an agent is a framework change. It needs the escalation
justification in `docs/RESEARCH_WORKFLOW.md` §12, an update to `AGENTS.md` §11 and to this
file, and `python scripts/sync_agents.py` in the same change.
